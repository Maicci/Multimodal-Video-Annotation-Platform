## Fixtures and synchronization method

Both fixtures are eight-second H.264/AAC MP4s generated by FFmpeg, with a moving
test pattern and an 80 ms, 200 Hz audio pulse at each whole second:

- CFR: 25 fps, 200 frames.
- VFR: 10 fps for the first four seconds, then 30 fps; 160 frames. The test
  asserts two different frame intervals, so a mistakenly converted CFR file fails.

The waveform artifact must contain a pulse within the first 100 ms of each
second and be quiet at each half-second. This checks waveform data placement
as well as navigation.

The measured playhead error is the larger of the waveform and thumbnail
playhead offsets from `HTMLVideoElement.currentTime`, read together in a browser
animation callback. UI coordinates are converted back to seconds using their
respective durations. The test also checks displayed frame numbers after seeks.
The independent frame timestamp comparison allows 1 microsecond rounding error.

Issue #38 specifies no numeric synchronization tolerance. This pass uses a
**100 ms maximum during playback**, **50 ms maximum after seeking**, and
30 ms maximum difference from pointer seek targets. These are explicit test
thresholds, not a claim that the original specification prescribed them.

| Browser | Clip | Samples | Maximum playback error | Maximum settled-seek error |
| --- | --- | ---: | ---: | ---: |
| Chromium 156.0.8078.80 | CFR | 181 | 17.574 ms | 0.003 ms |
| Chromium 156.0.8078.80 | VFR | 181 | 17.367 ms | 0.003 ms |
| Firefox 157.0 | CFR | 181 | 44.839 ms | 0.003 ms (rounded up) |
| Firefox 157.0 | VFR | 181 | 45.089 ms | 0.003 ms (rounded up) |

Before the fix, Chromium maximum playback errors were 259.974 ms (CFR) and
266.338 ms (VFR). The old display relied on native `timeupdate` events. The new
display reads the video clock on each animation frame during playback and keeps
`timeupdate` for paused seeks/background tabs. Displayed frame numbers now use
the downloaded timestamp map, avoiding a separate network request and delay.

These measurements cover foreground playback of the generated clips, not
physical speaker/display latency, long-recording drift, or every possible VFR
encoding. They do not measure Whisper accuracy.

## Reproduce and inspect

From the repository root:

```powershell
docker compose -f test-space/compose.yaml up -d --build backend frontend
docker compose -f test-space/compose.yaml exec -T -w /workspace/backend backend pytest -q
docker compose -f test-space/compose.yaml --profile e2e run --rm --build --no-deps e2e
docker compose -f test-space/compose.yaml --profile e2e run --rm --no-deps -e E2E_BROWSER=firefox e2e npx playwright test --config=tests/e2e/playwright.config.ts sprint2-acceptance.spec.ts
docker compose -f test-space/compose.yaml exec -T -w /workspace/frontend frontend npm run lint
docker compose -f test-space/compose.yaml exec -T -w /workspace/frontend frontend npx tsc -b --noEmit
docker compose -f test-space/compose.yaml exec -T -w /workspace/frontend frontend npm run build
```

The browser runs leave the local app running. Evidence is written to the ignored
`test-space/artifacts/<browser>/` directory:

- `results.json`: complete outcomes; `synchronization.json` attachments include
  every playback sample and exact browser versions.
- `html/index.html`: Playwright report.
- `test-results/`: `completed-workspace.png`, `narrow-workspace.png`, plus
  error context and traces on failure.

Each run replaces the previous results for that browser. GitHub Actions uploads
`test-space/artifacts/` as the `browser-test-results` artifact, even on failure.
The full Chromium suite is the default CI run; Firefox is an additional local
acceptance run. CI upload configuration has been added but awaits its first PR run.
